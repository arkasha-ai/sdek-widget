# Аркадиус — Sprint 1: Tech Backlog (2 недели)

> **Версия:** 1.0 | **Дата:** 2026-03-19  
> **Цель спринта:** Рабочий прототип — регистрация, чат с агентом, биллинг, деплой на Hetzner  
> **Команда:** 1-2 разработчика

---

## День 1–3: Инфраструктура и ядро

### T-01: Настройка Hetzner-сервера
- **Описание:** Поднять CPX41 (8 vCPU, 16GB RAM), настроить Ubuntu 24.04, firewall (ufw), fail2ban, SSH-keys, Docker для инфра-сервисов
- **Estimate:** 4ч
- **Зависимости:** —
- **Результат:** Сервер доступен по SSH, Docker работает, домен привязан (A-запись)

### T-02: Docker Compose для инфра-сервисов
- **Описание:** Развернуть docker-compose с PostgreSQL 16, Redis 7, Caddy (reverse proxy + auto-SSL). Файл `docker-compose.infra.yml`
- **Estimate:** 3ч
- **Зависимости:** T-01
- **Результат:** Сервисы запущены, PostgreSQL доступен, Caddy раздаёт SSL на домен

### T-03: Форк OpenClaw + первоначальная адаптация
- **Описание:** Создать приватный форк OpenClaw, убрать Telegram/WhatsApp каналы из default config, добавить WebChat channel stub. Настроить workspace-шаблон для новых пользователей: дефолтные SOUL.md, USER.md, MEMORY.md
- **Estimate:** 6ч
- **Зависимости:** —
- **Результат:** Форк в Git, запускается локально с шаблонным workspace

### T-04: Миграции БД (PostgreSQL)
- **Описание:** Создать схему БД: users, credit_balances, credit_transactions, token_usage, agent_configs, agent_sessions, user_files. Использовать Drizzle ORM или Prisma для миграций
- **Estimate:** 4ч
- **Зависимости:** T-02
- **Результат:** Миграции накатываются командой `npm run migrate`, seed с тестовым пользователем

### T-05: LiteLLM Proxy + billing callback
- **Описание:** Развернуть LiteLLM Proxy (Docker), настроить модели (Claude Sonnet, GPT-4o, Qwen Plus), написать custom success_callback который логирует usage в PostgreSQL и декрементирует баланс
- **Estimate:** 6ч
- **Зависимости:** T-02, T-04
- **Результат:** LiteLLM проксирует запросы, каждый запрос записывает usage в БД

### T-06: Инициализация фронтенд-проекта
- **Описание:** Next.js 15 (App Router) + Tailwind CSS + shadcn/ui. Настроить: layout, тему (тёмная по умолчанию), роутинг (/login, /register, /chat, /billing, /settings). ESLint + Prettier
- **Estimate:** 3ч
- **Зависимости:** —
- **Результат:** Проект стартует, пустые страницы рендерятся, деплой на сервер через Docker

## День 4–7: Auth + Billing

### T-07: API Gateway — базовый сервер
- **Описание:** Fastify-сервер с TypeScript. Middleware: CORS, rate limiting (Redis), request logging. Структура: `src/routes/`, `src/services/`, `src/middleware/`. Health-check эндпоинт
- **Estimate:** 4ч
- **Зависимости:** T-02
- **Результат:** `GET /api/health` отвечает 200, rate limiter блокирует при превышении

### T-08: Auth — регистрация и вход по email
- **Описание:** Эндпоинты: POST `/api/auth/register`, POST `/api/auth/login`, POST `/api/auth/logout`. Пароли: bcrypt. Сессии: в Redis (httpOnly cookie). Валидация: Zod-схемы
- **Estimate:** 6ч
- **Зависимости:** T-04, T-07
- **Результат:** Можно зарегистрироваться и войти через API, сессия в cookie

### T-09: Auth — Google OAuth
- **Описание:** GET `/api/auth/google` → redirect на Google, callback → создание/привязка аккаунта. Использовать Arctic или passport-google-oauth20
- **Estimate:** 4ч
- **Зависимости:** T-08
- **Результат:** «Войти через Google» работает end-to-end

### T-10: Фронтенд — экраны регистрации и входа
- **Описание:** Страницы /login и /register. Формы с валидацией (react-hook-form + zod). Кнопка Google OAuth. Обработка ошибок: «Email уже зарегистрирован», «Неверный пароль»
- **Estimate:** 5ч
- **Зависимости:** T-06, T-08
- **Результат:** Регистрация и вход работают в браузере

### T-11: Billing — API пополнения (ЮKassa)
- **Описание:** POST `/api/billing/topup` — создаёт платёж в ЮKassa, возвращает redirect URL. POST `/api/billing/webhook` — обрабатывает callback от ЮKassa, начисляет кредиты. GET `/api/billing/balance` — возвращает текущий баланс
- **Estimate:** 8ч
- **Зависимости:** T-04, T-07
- **Результат:** Тестовый платёж проходит в sandbox ЮKassa, кредиты начисляются

### T-12: Billing — pre-flight check
- **Описание:** Middleware в API Gateway: перед каждым LLM-запросом проверять `GET /api/billing/check?user_id=X&estimated_cost=Y`. При недостатке — 402 Payment Required. Агент перехватывает ошибку и сообщает пользователю
- **Estimate:** 3ч
- **Зависимости:** T-05, T-11
- **Результат:** При нулевом балансе агент отказывается обрабатывать и предлагает пополнить

## День 8–10: Основной UI

### T-13: Фронтенд — экран чата (основной)
- **Описание:** Страница /chat. Компоненты: ChatMessage (user/agent), MessageInput (textarea + send button + file attach), ChatHeader (имя агента, баланс, модель). WebSocket подключение для стриминга. Markdown-рендеринг (react-markdown + rehype-highlight)
- **Estimate:** 10ч
- **Зависимости:** T-06, T-10
- **Результат:** Сообщения отправляются и ответы агента стримятся в реальном времени

### T-14: WebSocket Gateway
- **Описание:** WS-эндпоинт `/api/chat/stream`. Аутентификация по session cookie. Формат: JSON messages `{type: "token" | "done" | "tool_start" | "tool_end" | "error", data: ...}`. Подключение агента через pipe stdout → WS
- **Estimate:** 6ч
- **Зависимости:** T-07, T-08
- **Результат:** Стриминг ответа агента работает end-to-end

### T-15: Control Plane — lifecycle агентов
- **Описание:** Сервис управления агентами: `startAgent(userId)` — запуск процесса OpenClaw с workspace пользователя; `stopAgent(userId)` — graceful shutdown; `sendMessage(userId, text)` — отправка в stdin агента. Auto-sleep через 10 мин бездействия. Лимит одновременных агентов (50 для MVP)
- **Estimate:** 10ч
- **Зависимости:** T-03, T-05, T-07
- **Результат:** Агент просыпается при сообщении, обрабатывает, засыпает через 10 мин

### T-16: Фронтенд — экран пополнения баланса
- **Описание:** Страница /billing. Пакеты (карточки): 199₽, 499₽, 999₽, 2999₽ + поле произвольной суммы. Кнопка → redirect на ЮKassa → return URL обратно. Текущий баланс + история пополнений (таблица)
- **Estimate:** 5ч
- **Зависимости:** T-06, T-11
- **Результат:** Пользователь может пополнить баланс через UI

### T-17: Фронтенд — онбординг
- **Описание:** Страница /onboarding (3 шага). Step 1: «Как вас зовут?» (input). Step 2: «Назовите агента» (input + предложения). Step 3: «Для чего вам ассистент?» (выбор: работа/учёба/личное). POST данных → создание workspace + agent_config. Redirect на /chat
- **Estimate:** 5ч
- **Зависимости:** T-06, T-08, T-15
- **Результат:** Новый пользователь проходит онбординг и попадает в чат с настроенным агентом

## День 11–14: Интеграция, тесты, деплой

### T-18: Загрузка файлов
- **Описание:** POST `/api/files/upload` — multer, сохранение в workspace агента `/files/`. Фронт: кнопка 📎 в ChatInput, drag-and-drop. Превью загруженного файла в чате. Лимит: 25MB, форматы: PDF, DOCX, TXT, PNG, JPG, CSV
- **Estimate:** 5ч
- **Зависимости:** T-13, T-15
- **Результат:** Файлы загружаются и агент может их читать/анализировать

### T-19: Фронтенд — настройки агента
- **Описание:** Страница /settings. Секции: профиль пользователя (имя, email), настройки агента (имя, модель, системный промпт), сессия (выйти). PATCH `/api/agent/config` для сохранения
- **Estimate:** 4ч
- **Зависимости:** T-06, T-08
- **Результат:** Пользователь меняет модель/имя агента через UI

### T-20: Фронтенд — история расходов
- **Описание:** Страница /usage. Таблица: дата, тип, модель, токены, стоимость. Фильтры по дате. Сводка: общий расход, средний в день. GET `/api/billing/usage?from=X&to=Y`
- **Estimate:** 4ч
- **Зависимости:** T-06, T-11
- **Результат:** Пользователь видит детализацию расходов

### T-21: E2E тесты критического пути
- **Описание:** Playwright-тесты: 1) регистрация → онбординг → чат; 2) отправка сообщения → получение ответа; 3) пополнение (mock ЮKassa webhook) → баланс обновился; 4) загрузка файла → агент видит файл. CI: GitHub Actions
- **Estimate:** 6ч
- **Зависимости:** T-10, T-13, T-16, T-17, T-18
- **Результат:** 4 E2E-теста проходят в CI

### T-22: CI/CD Pipeline
- **Описание:** GitHub Actions: lint → test → build → deploy (SSH + docker-compose pull + restart). Два окружения: staging (ветка dev) и production (ветка main). Health-check после деплоя
- **Estimate:** 4ч
- **Зависимости:** T-01, T-02
- **Результат:** Push в main → автодеплой на сервер за 3-5 минут

### T-23: Мониторинг и алерты
- **Описание:** Docker: Prometheus + Grafana. Метрики: CPU/RAM сервера, кол-во активных агентов, avg response time, errors/min, LLM cost/hour. Алерт в Telegram при: CPU >80%, agent crash, LLM errors >10/min
- **Estimate:** 5ч
- **Зависимости:** T-01, T-02, T-15
- **Результат:** Grafana-дашборд с основными метриками, алерты работают

### T-24: Финальная интеграция и баг-фикс
- **Описание:** Прогон всего флоу end-to-end. Исправление найденных багов. Проверка: cold start агента < 2 сек, стриминг работает без разрывов, биллинг считает корректно, файлы загружаются
- **Estimate:** 8ч
- **Зависимости:** Все задачи
- **Результат:** MVP работает стабильно, готов для закрытого бета-тестирования
