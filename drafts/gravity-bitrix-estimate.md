# Альтернативная оценка: Единая мультиканальная платформа на базе 1С-Битрикс Управление Сайтом (БУС)

**Проект:** retail-сеть, 10 магазинов, 10 000 SKU, 100 категорий  
**Дата оценки:** апрель 2026  
**Основание:** ТЗ заказчика (веб-витрина, мобильное приложение, админка, МойСклад, платежи, AI, маркетплейсы, Mini Apps)

---

## 1. Анализ возможностей БУС

### 1.1 Что даёт из коробки (редакция "Бизнес", 96 500 руб.)

| Возможность | Статус | Примечание |
|---|---|---|
| Каталог товаров (категории, SKU, цены, характеристики) | Из коробки | Полноценно для 10 000 SKU |
| Мультисклад (остатки по складам) | Из коробки | Есть модуль "Складской учет", но ограниченная логика |
| Корзина и оформление заказа | Из коробки | |
| Личный кабинет клиента | Из коробки | |
| Админка (управление каталогом, заказами, пользователями) | Из коробки | Штатная, требует кастомизации |
| OpenSearch / фильтрация | Из коробки | Elasticsearch из коробки в Бизнес |
| SEO (мета-теги, чпу, sitemap) | Из коробки | |
| Рассылки, email | Из коробки | |
| Мобильная платформа | Из коробки | Cordova, не нативный React Native |
| Модуль "Веб-сервисы" (REST API) | Из коробки | Ограниченный, D7 требует доработок |
| Интеграция с 1С | Из коробки | **Не с МойСкладом!** |
| Интеграция с CRM Битрикс24 | Из коробки | |
| Маркетплейс модулей | Да | Есть готовые модули, но не для WB/Ozon |
| Выгрузка в Яндекс.Маркет | Из коробки | Не WB/Ozon |

### 1.2 Что не даёт или даёт плохо

| Возможность | Проблема | Решение |
|---|---|---|
| Интеграция с МойСклад | Нет готового модуля, БУС работает только с 1С | Кастомный модуль (REST API МойСклад) |
| Мобильное приложение (нативное) | Штатное — Cordova (гибридное), low quality | React Native |
| AI-функции (поиск, рекомендации, генерация описаний) | Нет | Отдельный микросервис |
| Маркетплейсы WB / Ozon | Нет готовых интеграций | Кастомные адаптеры |
| Mini Apps (Telegram, VK) | Нет | Web-view обёртка |
| API-first архитектура | Встроенный REST ограничен, D7 сыроват | Расширение API (GraphQL/REST) |
| Гибкая мультискладовость | Базовый учёт есть, но сложная логика (резервы, трансферы) требует доработки | Кастомная логика |
| Vendor lock-in | PHP/Bitrix-специфичный код, зависимость от экосистемы | PHP/Bitrix-компетенция обязательна |

## 3. Кастомная разработка: компоненты и оценка трудоёмкости

### 3.1 МойСклад модуль (двусторонняя синхронизация)

**Что делаем:**
- Синхронизация товаров: создание/обновление/удаление товаров и SKU (characteristics, offers)
- Синхронизация остатков: получение остатков из МойСклад, распределение по складам БУС
- Синхронизация цен: загрузка цен из МойСклад, применение наценок
- Синхронизация заказов: создание заказов в МойСклад при оформлении на сайте, обновление статусов
- Синхронизация контрагентов: физлица/юрлица из МойСклад
- Обработка вебхуков МойСклад (stock changed, order changed)
- Маппинг складов: 10 складов МойСклад — склады БУС
- Очередь синхронизации (supplier_id, delta-обновления)

| Параметр | Значение |
|---|---|
| Min | 20 ч/дней |
| Realistic | 30 ч/дней |
| Max | 45 ч/дней |
| Сложность | Высокая. API МойСклад нестабилен, много edge-cases по статусам и складским трансферам |

---

### 3.2 Мобильное приложение (React Native)

**Что делаем:**
- Каталог: дерево категорий, карточка товара, характеристики, торговые предложения
- Поиск: текстовый + фильтры (цена, бренд, характеристики)
- Корзина: добавление, редактирование количества, применение промокодов
- Оформление заказа: выбор склада самовывоза, доставка, СБП-оплата
- Личный кабинет: история заказов, профиль, адреса, избранное
- Push-уведомления: FCM (Android) + APNs (iOS), нотификации о статусах заказов
- Авторизация:phone / email + код, интеграция с БУС (rest API)
- Офлайн-режим: кеширование каталога, отложенные действия

| Параметр | Значение |
|---|---|
| Min | 40 ч/дней |
| Realistic | 60 ч/дней |
| Max | 85 ч/дней |
| Сложность | Высокая. 10 000 SKU — нужна пагинация, lazy load, кеширование. СБП в мобильном — отдельная интеграция с ЮKassa |

---

### 3.3 API-расширение для БУС (GraphQL / расширенный REST)

**Что делаем:**
- GraphQL-схема: Products, Categories, Cart, Orders, Stocks, Users
- Подписки на изменения ( websockets для real-time остатков)
- Расширение REST: эндпоинты для мобильного приложения (минуя штатный limited API)
- Аутентификация: JWT, refresh-token, OAuth для маркетплейсов
- Rate limiting, кеширование на уровне API
- Документация (OpenAPI 3.0)

| Параметр | Значение |
|---|---|
| Min | 15 ч/дней |
| Realistic | 22 ч/дня |
| Max | 35 ч/дней |
| Сложность | Средняя. Основной риск — производительность GraphQL на 10 000 SKU (нужен DataLoader) |

---

### 3.4 AI-микросервис (Python / FastAPI)

**Что делаем:**

**а) Семантический поиск:**
- Индексация 10 000 товаров (название, описание, характеристики)
- Векторизация через embedding-модель (sentence-transformers или облачный API)
- Хранение векторов в Qdrant / Chroma
- Поиск по семантике (векторное сходство), fallback в текстовый

**б) Рекомендательная система:**
- Collaborative filtering (покупки, просмотры)
- Content-based (по категориям, характеристикам)
- A/B-тестирование гипотез

**в) Генерация описаний товаров (LLM):**
- Генерация SEO-описаний для товаров без описания
- Краткие характеристики (3-5 тезисов)
- Интеграция с LLM API (OpenAI / Claude / Yandex GPT)

| Параметр | Значение |
|---|---|
| Min | 25 ч/дней |
| Realistic | 40 ч/дней |
| Max | 60 ч/дней |
| Сложность | Высокая. Обучение векторного индекса, интеграция LLM (стоимость, rate limiting), поддержка актуальности данных |

---

### 3.5 Интеграция маркетплейсов (WB + Ozon)

**Что делаем:**

**а) Wildberries:**
- Выгрузка товаров (карточки, цены, остатки) по API v2/v3
- Обработка заказов (сборка, отгрузка, возврат)
- Синхронизация остатков (stock deduction при продаже на WB)
- Отчёты и статистика

**б) Ozon:**
- API v2: товары (создание/обновление карточек)
- FBO / FBS логистика: управление поставками
- Цены и акции
- Отчёты

| Параметр | Значение |
|---|---|
| Min | 22 ч/дня |
| Realistic | 35 ч/дней |
| Max | 55 ч/дней |
| Сложность | Высокая. API WB и Ozon постоянно меняются, сложная логика остатков (нельзя уйти в минус на нескольких площадках), разные схемы работы (FBO/FBS) |

---

### 3.6 Мультисклад-логика в админке

**Что делаем:**
- Расширенный складской учёт: резервирование товаров под заказ
- Внутренние перемещения между 10 складами (трансферы)
- Приоритизация складов при резервировании (ближайший, с наличием)
- Отчёты: остатки по каждому складу, ABC-анализ
- Интеграция с трансферами МойСклад (движение товара между точками)
- Ролевая модель: менеджер склада видит только свой склад, админ — все

| Параметр | Значение |
|---|---|
| Min | 12 ч/дней |
| Realistic | 20 ч/дней |
| Max | 32 ч/дня |
| Сложность | Средняя. Основная сложность — корректное резервирование при мультиканальных заказах (онлайн + офлайн) |

---

### 3.7 Кастомная админка (BI-дашборды, расширенное управление заказами)

**Что делаем:**
- BI-дашборды: выручка, средний чек, конверсия, топ товары, динамика по складам
- Расширенное управление заказами: массовые действия, автоматизация статусов, причины возвратов
- CRM-функции (если не используется отдельная CRM): карточка клиента, история покупок, сегментация
- Управление скидками и промокодами (расширенное, сверх штатного)
- Уведомления менеджеров (telegram bot / email при событиях)

| Параметр | Значение |
|---|---|
| Min | 18 ч/дней |
| Realistic | 28 ч/дней |
| Max | 42 ч/дня |
| Сложность | Средняя. BI-дашборды — основной риск (нужно data layer, пайплайн данных) |

---

### 3.8 Платёжный модуль (ЮKassa, СБП)

**Что делаем:**
- ЮKassa: приём платежей (банковские карты, СБП, QR, SBP)
- СБП (Система быстрых платежей): интеграция через ЮKassa API
- Эквайринг: приём платежей, возврат, рефанд
- Статусовая модель: pending -> confirmed -> cancelled / refunded
- Платёжные ссылки (для некоторых сценариев оплаты)
- Обработка webhook от ЮKassa

| Параметр | Значение |
|---|---|
| Min | 10 ч/дней |
| Realistic | 15 ч/дней |
| Max | 22 ч/дня |
| Сложность | Средняя. Штатный модуль ЮKassa для БУС покрывает базовые сценарии, но СБП и возвратная логика — кастом |

---

### 3.9 Мини-приложения (Telegram, VK)

**Что делаем:**
- Telegram Mini App: web-view обёртка над веб-витриной БУС
- VK Mini App: аналогично
- Авторизация через платформу (Telegram User ID / VK ID)
- Адаптивный UI для мобильных экранов
- Push через платформенные каналы (Telegram Bot / VK Callback)

| Параметр | Значение |
|---|---|
| Min | 8 ч/дней |
| Realistic | 12 ч/дней |
| Max | 18 ч/дней |
| Сложность | Низкая-средняя. По сути — адаптивная вёрстка + авторизация. Основной риск — ограничения платформ (Telegram WebView, VK Mini App rules) |

## 6. Сравнение: кастом vs БУС

| Параметр | Кастом (оценка 1) | БУС (оценка 2) |
|---|---|---|
| **Бюджет** | 17.7 — 36.9 млн ₽ | **2.8 — 5.7 млн ₽** |
| **Срок до MVP** | 4.5 — 8 мес. | **4 мес.** |
| **Срок до Production (full)** | 6 — 10 мес. | **6 — 7 мес.** |
| **Гибкость архитектуры** | Высокая (микросервисы, API-first) | Средняя (PHP/Bitrix-специфика, D7) |
| **Масштабируемость** | Высокая (K8s, горизонтальное масштабирование) | Ограниченная (VDS, PHP Sessions, Bitrix VM) |
| **AI-возможности** | Полный контроль, интеграция любых моделей | Свой микросервис (одинаково для обоих вариантов) |
| **МойСклад интеграция** | Своя (такой же кастом) | Кастомный модуль (такой же объём работ) |
| **Мобильное приложение** | React Native с чистым API | React Native, но с дополнительным слоем (API БУС) |
| **Vendor lock-in** | Отсутствует (своя инфраструктура) | **Сильный** (PHP/Bitrix, привязка к редакции, обновления ломают кастом) |
| **Стоимость владения (3 года)** | ~30 — 50 млн (разработка + поддержка) | ~8 — 15 млн (лицензия + хостинг + поддержка) |
| **Возможность миграции** | Полная | Сложная (Bitrix-специфичный код, данные в формате БУС) |
| **Штатная поддержка** | Своя команда | 1С-Битрикс (техподдержка платформы), партнёры |
| **Time to market (full)** | 6 — 10 мес. | **5 — 7 мес.** |

## 7. Рекомендация

### 7.1 Когда БУС имеет смысл

- **Быстрый старт критичен.** БУС даёт веб-витрину, каталог, заказы, админку за 1-2 месяца конфигурации (без кастомной разработки).
- **SEO и маркетинг важны, но не критичны к производительности.** БУС имеет встроенные инструменты SEO, рассылок, аналитики.
- **Команда имеет компетенцию в Bitrix/PHP.** Кастомный код на БУС — это PHP/Bitrix D7. Если команды с этой компетенцией нет, порог входа высок.
- **Бюджет ограничен, риск высокий.** Кастом за 17+ млн — это большой риск для заказчика. БУС за 3-5 млн — снижает риск на старте.
- **Первая версия — проверка гипотезы.** Retail-сеть 10 магазинов — это не стартап, но MVP на БУС позволит проверить модель без полной перестройки.

### 7.2 Когда нужен кастом

- **Гибкость масштабирования критична.** 10 складов, 10 000 SKU, маркетплейсы, AI — всё это генерирует нагрузку, с которой PHP-монолит на VDS справится ограниченно.
- **Долгосрочная стратегия digital-first.** Если онлайн-продажи — основной канал, лучше инвестировать в чистую архитектуру.
- **Команда заказчика — техническая.** Кастомное решение требует своей команды поддержки (DevOps, PHP, Python, React Native).
- **Интеграция с нестандартным оборудованием / процессами.** БУС — это коробка, любое отклонение — кастом.

### 7.3 Честный вывод для данного проекта

Для ТЗ заказчика (10 000 SKU + МойСклад + AI + маркетплейсы + мультисклад + мобильное приложение) **БУС покрывает из коробки ~40-50% функционала**. Остальное — кастом:

```
БУС даёт:          ~40% работ (веб-витрина, каталог, заказы, админка базовая)
Кастом на БУС:     ~60% работ (МойСклад, AI, маркетплейсы, мобильное, мультисклад)
Кастом полный:      100% работ (но свой фундамент)
```

**БУС в этом проекте — это фундамент, а не готовое решение.** Разница с полностью кастомным подходом — не в объёме кастомной разработки (60% vs 100%), а в стоимости и сроках:

- **Кастом (17.7-36.9 млн):** платите за фундамент + кастом, свой код, своя инфраструктура
- **БУС (2.8-5.7 млн):** платите за фундамент (БУС) + кастом (те же 60% задач), но часть задач уже решена коробкой

Экономия ~3-6x на фундаменте — это основное преимущество БУС. Однако нужно быть готовым к vendor lock-in, ограничениям масштабирования и затратам на PHP/Bitrix-компетенцию.

### 7.4 Практическая рекомендация

| Сценарий | Подход |
|---|---|
| Ограниченный бюджет (< 10 млн), первый запуск | **БУС (Бизнес)** — минимизировать кастом, взять MVP (п. 4.1) |
| Средний бюджет (10-20 млн), есть план роста | **БУС на старт**, через 6-12 мес. оценить миграцию критичных компонентов |
| Большой бюджет (> 20 млн), масштабирование критично | **Кастом** — инвестиции окупятся на горизонте 2-3 лет |
| Команда заказчика — техническая | **Кастом** — больше контроля, меньше vendor lock-in |
| Команда заказчика — нетехническая | **БУС** — проще поддержка через партнёров 1С-Битрикс |
