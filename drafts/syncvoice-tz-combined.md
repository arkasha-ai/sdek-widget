# SyncVoice™ — Требования к системе
> Версия 0.2 | 22.02.2026

---

## 1. Общее описание

**SyncVoice** — on-premise платформа синхронного речевого перевода в реальном времени для конференций. Система переводит речь каждого участника на языки остальных и воспроизводит перевод через браузер. Оригинальный голос не передаётся другим участникам.

---

## 2. Функциональные требования

### 2.1 Конференция и участники

- **FR-01** Система поддерживает одновременно несколько независимых конференций (комнат)
- **FR-02** Максимальное число участников на конференцию задаётся при установке системы исходя из характеристик железа
- **FR-03** При достижении лимита участников система блокирует новые подключения к данной конференции
- **FR-04** Модератор при создании конференции задаёт лимит участников (не выше системного максимума)
- **FR-05** Модератор может заранее создать конференцию и получить ссылку для рассылки
- **FR-06** Каждый участник выбирает свой язык при входе; несколько участников могут иметь одинаковый язык
- **FR-07** Участник слышит только TTS-аудио на своём языке; оригинальные голоса других участников не передаются
- **FR-08** Участник не получает перевод своей собственной речи

### 2.2 Перевод

- **FR-09** Поддерживаемые языки на старте: English (EN), Русский (RU), Hindi (HI)
- **FR-10** Архитектура позволяет добавлять новые языки (например, китайский) без переработки ядра
- **FR-11** Целевая задержка от конца фразы до начала воспроизведения перевода: **≤2 секунды**
- **FR-12** Один перевод на пару (язык источника → язык цели) раздаётся всем участникам с этим языком — без дублирования вычислений
- **FR-13** Речь делится на осмысленные фрагменты (VAD-based chunking) и отправляется в pipeline по мере обнаружения пауз — без ожидания конца всей фразы
- **FR-14** При перегрузке pipeline (все участники говорят одновременно) фрагменты встают в очередь; пропуска данных не происходит

### 2.3 Веб-клиент

- **FR-15** Доступ через браузер без установки дополнительного ПО; поддержка Chrome, Firefox, Safari, Edge; мобильные браузеры (iOS Safari, Android Chrome)
- **FR-16** Интерфейс: выбор языка при входе, видео участников, управление микрофоном и камерой (вкл/выкл), выход
- **FR-17** Демонстрация экрана (screen sharing) из браузера
- **FR-18** Список участников с именами и выбранными языками
- **FR-19** Визуальные индикаторы состояния для каждого участника:
  - 🎙 **Говорит** — VAD детектировал речь, идёт накопление фрагмента
  - ⚙️ **Обрабатывается** — фрагмент отправлен в translation pipeline
  - ✅ **Готово** — перевод воспроизводится
- **FR-20** Статус подключения и текущая latency перевода
- **FR-21** White-label: клиент может загрузить свой логотип и настроить цвета интерфейса

### 2.4 Авторизация и управление пользователями

- **FR-22** Аутентификация: логин + пароль
- **FR-23** Роли:
  - **Администратор** — полный доступ: пользователи, настройки системы, глоссарии, записи
  - **Модератор** — создаёт конференции, управляет участниками во время сессии, доступ к своим записям
  - **Участник** — присоединяется к назначенной конференции
  - **Гость** — присоединяется по ссылке без логина: вводит имя и выбирает язык
- **FR-24** Администратор управляет пользователями: создание, редактирование, блокировка
- **FR-25** Модератор может ограничить доступ гостей к конкретной конференции

### 2.5 Глоссарий (GlossaryAI)

- **FR-26** Управление глоссарием терминов (CRUD): создание, редактирование, удаление; поддержка 2000+ терминов
- **FR-27** Импорт терминов из Excel / CSV
- **FR-28** Приоритет терминов глоссария при переводе (constrained decoding или post-processing)
- **FR-29** Правила "не переводить" для кодов, аббревиатур, названий препаратов
- **FR-30** Фонетические транскрипции для корректного произношения TTS
- **FR-31** Версионирование глоссариев с возможностью отката

### 2.6 Запись конференций

- **FR-32** Запись конференции в стиле Zoom: активный говорящий крупным планом + галерея; при демонстрации экрана — экран основным видом
- **FR-33** Запись TTS-аудио по каждому языку конференции как отдельные аудиодорожки
- **FR-34** Итоговый файл: **MP4** с видео + N аудиодорожек (по одной на язык); при воспроизведении можно выбрать язык озвучки
- **FR-35** Доступ к записям через Admin Portal; скачивание
- **FR-36** Настройка политики хранения (время жизни записей)

### 2.7 Admin Portal

- **FR-37** Дашборд в реальном времени: активные конференции, число участников, GPU нагрузка, latency
- **FR-38** Мониторинг и алерты: уведомление администратора при превышении latency, падении компонентов, перегрузке GPU
- **FR-39** Управление пользователями и ролями
- **FR-40** Управление глоссариями
- **FR-41** История сессий и архив записей
- **FR-42** Настройки системы: доступные языки, лимит участников, параметры VAD, white-label

## 3. Нефункциональные требования

### 3.1 Производительность

- **NFR-01** Задержка end-to-end p95 ≤ 2 секунды (от конца фразы до начала воспроизведения)
- **NFR-02** При перегрузке — очередь без потери данных; визуальная индикация состояния для участников
- **NFR-03** Поддержка нескольких параллельных конференций в рамках GPU-лимита инсталляции

### 3.2 Деплой

- **NFR-04** On-premise: клиент подключается по IP к серверу в своей сети
- **NFR-05** Поддержка четырёх аппаратных конфигураций:
  - **NVIDIA-сервер A100/A10**: Full Docker + NVIDIA Container Toolkit + CUDA
  - **NVIDIA-сервер RTX 4090/5090**: Full Docker + NVIDIA Container Toolkit + CUDA
  - **Apple Mac Studio** (M2/M3/M4 Ultra): гибридный деплой — сервисы в Docker Desktop, Translation Agent нативно через PyTorch MPS
  - **NVIDIA DGX Spark** (GB10): Full Docker + NVIDIA Container Toolkit + CUDA
- **NFR-06** Встроенный TURN/STUN сервер для NAT traversal внутри сети клиента
- **NFR-07** Документация по установке для каждой из трёх аппаратных конфигураций

### 3.3 Безопасность

- **NFR-08** TLS для всех соединений (WebRTC, API, Admin Portal)
- **NFR-09** Шифрование данных at rest (записи, глоссарии)
- **NFR-10** Zero external calls — вся обработка на машине клиента, интернет не требуется
- **NFR-11** Аудит-лог действий пользователей

### 3.4 Расширяемость

- **NFR-12** Новый язык добавляется через конфиг + языковую модель без переработки кода
- **NFR-13** Translation backend заменяем (SeamlessM4T → другая модель) без изменений в pipeline

# 5. Архитектура системы

> Раздел технического задания SyncVoice™ v0.2

---

## 5.1 Обзор архитектуры

### Общая схема компонентов

![Общая архитектура SyncVoice](img/syncvoice-arch-overview.png)

### Принцип работы (краткое описание)

1. **Участник** открывает ссылку в браузере, выбирает язык и подключается к конференции через WebRTC.
2. **LiveKit SFU** принимает аудио и видео от каждого участника и раздаёт видео всем остальным.
3. **Translation Agent** получает аудио каждого говорящего, определяет момент окончания фразы (VAD) и отправляет фрагмент на перевод.
4. **SeamlessM4T v2** на GPU переводит речь на каждый целевой язык и генерирует синтезированное аудио; GlossaryAI применяет терминологию.
5. **Переведённое аудио** публикуется обратно в LiveKit как отдельный трек для каждого языка — участники слышат только перевод на свой язык.
6. **Recording Service** параллельно записывает видео и все языковые аудиодорожки в единый MP4-файл.
7. **Admin Portal** позволяет управлять конференциями, пользователями, глоссариями и просматривать записи.

## 5.2 Компоненты системы

### 5.2.1 WebRTC SFU — LiveKit Server

| Параметр | Значение |
|----------|----------|
| **Назначение** | Приём и маршрутизация аудио/видео потоков между участниками и агентами |
| **Технология** | LiveKit (Go), self-hosted |
| **Лицензия** | Apache 2.0 |

**Почему LiveKit:**
- Первоклассный Python SDK (LiveKit Agents) — подписка на audio tracks, обработка и публикация обратно без GStreamer/FFmpeg
- Модель Rooms + Tracks — один published track раздаётся множеству подписчиков без дублирования
- Встроенная поддержка TURN/STUN, Data Channels для метаданных
- On-premise деплой — один Docker-контейнер

### 5.2.2 Translation Agent

| Параметр | Значение |
|----------|----------|
| **Назначение** | VAD-детекция, chunking речи, оркестрация translation pipeline |
| **Технология** | Python 3.11+ / asyncio / LiveKit Agents SDK |
| **VAD** | Silero VAD (ONNX, ~2MB, ~30ms latency per frame) |

**Функции:**
- Подписка на audio track каждого участника через LiveKit Agents SDK
- VAD: определение начала/конца фразы (Silero VAD, порог 0.5, пауза ≥500ms)
- Adaptive chunking: разделение речи на фрагменты 1–4 секунды
- Принудительный split при непрерывной речи >5 секунд (с overlap 300ms для контекста)
- Fanout: для каждого фрагмента — запуск перевода на все целевые языки параллельно
- Публикация TTS-аудио как именованных треков в LiveKit

### 5.2.3 Translation Model — SeamlessM4T v2

| Параметр | Значение |
|----------|----------|
| **Назначение** | End-to-end перевод речи: ASR + NMT + TTS в одной модели |
| **Технология** | SeamlessM4T v2 Large (Meta, PyTorch) |
| **Лицензия** | CC BY-NC 4.0 (коммерческая лицензия обсуждается отдельно) |
| **Языки** | EN, RU, HI (100+ поддерживаемых) |
| **RTF** | ~0.5–0.8 на A100 (batch mode) |

**Почему SeamlessM4T v2:**
- Единственная open-source E2E модель с поддержкой S2ST (speech-to-speech translation) для EN/RU/HI
- Одна модель заменяет каскад ASR → NMT → TTS: меньше точек отказа, проще деплой
- RTF <1.0 на A100 — реальное время достижимо
- Расширяемость: добавление языков без изменения архитектуры

**Fallback-стратегия:** SeamlessStreaming (S2TT) + внешний TTS для сценариев с жёсткими требованиями к latency (~2–2.7s vs ~2–3s batch).

### 5.2.4 GlossaryAI

| Параметр | Значение |
|----------|----------|
| **Назначение** | Применение доменной терминологии к результату перевода |
| **Технология** | Python-модуль, post-processing |

**Механизм работы:**
1. После ASR-этапа (или из промежуточного текста SeamlessM4T) извлекается текстовое представление перевода
2. GlossaryAI выполняет поиск по словарю терминов (trie / hash-lookup, <1ms)
3. Замена терминов по правилам: точное совпадение, «не переводить», фонетическая транскрипция
4. Скорректированный текст подаётся на TTS-этап (если каскадный режим) или применяется как constrained output

**Поддержка:** 2000+ терминов, импорт из CSV/Excel, версионирование с откатом.

## 5.3 Поток данных (Data Flow)

### Один цикл перевода — детальная схема

![Поток данных — цикл перевода](img/syncvoice-dataflow.png)

**ИТОГО end-to-end latency (p95): ≤2 секунды** = ~100ms (сеть) + ~500-1500ms (VAD/chunk) + ~500-800ms (модель, A100) + ~100ms (сеть)

### Место GlossaryAI в pipeline

GlossaryAI работает на этапе 4 — между NMT и TTS:

**Audio → ASR → текст (source) → NMT → текст (target) → GlossaryAI → TTS → audio**

GlossaryAI выполняет: поиск по словарю, замену терминов, правила «не переводить», фонетические транскрипции.

В режиме end-to-end (SeamlessM4T S2ST) GlossaryAI применяется как post-processing к промежуточному текстовому представлению с повторной генерацией TTS для изменённых сегментов.

## 5.4 Маршрутизация потоков по языкам

### Схема N участников × M языков

Для конференции с 10 участниками и 3 языками (EN=3, RU=4, HI=3):

![Маршрутизация потоков N x M](img/syncvoice-routing.png)

### Оптимизация: один перевод на языковую пару

Ключевой принцип — **перевод выполняется один раз для пары (говорящий, целевой язык)**. Результат публикуется как один LiveKit audio track, на который подписываются все участники с данным языком.

**Пример:** Говорящий A1 (EN) произнёс фразу → translate(EN→RU) = 1 вызов модели → track "tts-ru-from-A1" (подписаны: B1–B4) → translate(EN→HI) = 1 вызов → track "tts-hi-from-A1" (подписаны: C1–C3). **Итого: 2 вызова модели вместо 7.**

### Количество translation jobs

| Метрика | Формула | Пример (10 уч., 3 языка) |
|---------|---------|--------------------------|
| Переводов на одного говорящего | M − 1 (число целевых языков) | 2 |
| Max concurrent (все говорят) | N × (M − 1) | 20 |
| Реалистичный concurrent | 1–2 говорящих × (M − 1) | 2–4 |

### Схема подписок (кто какой track получает)

| Участник | Язык | Подписан на tracks | НЕ подписан |
|----------|------|--------------------|-------------|
| A1 (EN) | EN | tts-en-from-B*, tts-en-from-C* | tts-en-from-A1 (свой), tts-ru-*, tts-hi-* |
| B1 (RU) | RU | tts-ru-from-A*, tts-ru-from-C* | tts-ru-from-B* (свои), tts-en-*, tts-hi-* |
| C1 (HI) | HI | tts-hi-from-A*, tts-hi-from-B* | tts-hi-from-C* (свои), tts-en-*, tts-ru-* |

Управление подписками реализовано на стороне LiveKit через Server SDK: при подключении участника агент устанавливает track subscription rules на основе выбранного языка.

## 5.5 Архитектура записи

### Структура записи конференции

![Архитектура записи конференции](img/syncvoice-recording.png)

### Детали реализации

- **Video compositing**: LiveKit Egress поддерживает composite layout (active speaker + grid). Настраивается через Egress API при старте записи.
- **Audio tracks**: каждый языковой TTS-track миксуется в отдельную аудиодорожку. FFmpeg объединяет video + N audio в мультидорожечный MP4.
- **Хранение**: локальная файловая система сервера. Политика retention настраивается в Admin Portal.
- **При воспроизведении**: пользователь выбирает языковую дорожку в плеере (VLC, браузерный плеер с выбором track).

## 5.6 Деплой

### Docker Compose — схема контейнеров

```yaml
# docker-compose.yml (схема)
services:
  livekit:          # LiveKit SFU Server
    image: livekit/livekit-server
    ports: [7880, 7881, 7882]  # HTTP, RTC (TCP/UDP)
    depends_on: [redis]

  translation-agent: # Translation Agent (Python)
    build: ./agent
    runtime: nvidia   # GPU доступ
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]
    depends_on: [livekit, redis, postgres]

  glossary-ai:       # GlossaryAI Service
    build: ./glossary
    depends_on: [postgres, redis]

  recording:         # Recording Service
    build: ./recording
    volumes: [recordings:/data/recordings]
    depends_on: [livekit]

  admin-portal:      # Admin Portal (React + API)
    build: ./admin
    ports: [443]
    depends_on: [postgres, redis, livekit]

  postgres:          # PostgreSQL
    image: postgres:16
    volumes: [pgdata:/var/lib/postgresql/data]

  redis:             # Redis
    image: redis:7-alpine

  coturn:            # TURN/STUN Server
    image: coturn/coturn
    ports: [3478, 5349]  # STUN/TURN
    network_mode: host
```

## 6.2 Детализация критических рисков

### T1 — Latency >2s на production-железе 🔴

**Описание:** На демо SeamlessM4T работал в идеальных условиях. В production добавляются: реальная сеть клиента, concurrent processing, холодный старт модели, накладные расходы Docker. Реальный p95 может составить 3–5s.

**Митигация:**
- Нагрузочный тест на железе клиента в первые 2 недели разработки
- Зафиксировать достигнутый p95 как contractual SLA — не абстрактное "≤2s"
- Если тест показывает >2s — согласовать с клиентом либо обновление железа, либо пересмотр SLA

**Ранний сигнал:** На 4-й неделе MVP показывает latency >3s на 2 участниках.

---

### T4 — Concurrent speakers ломают pipeline 🔴

**Описание:** При 3+ одновременно говорящих очередь translation jobs растёт быстрее чем GPU её обрабатывает. Latency деградирует до 10–15s. Формально система не падает, но UX катастрофический.

**Митигация:**
- Механизм очереди с приоритетами и "skip при перегрузке" проектируется с первого дня, не добавляется потом
- Стресс-тест: симуляция 10 одновременно говорящих обязателен до сдачи MVP
- Визуальный индикатор загрузки pipeline — участник видит что его речь обрабатывается
- Мониторинг глубины очереди в Admin Portal с алертами

**Ранний сигнал:** При тесте с 3+ участниками latency нестабильна (разброс >2x от среднего).

---

### P1 — Timeline недооценён 🔴

**Описание:** WebRTC + ML pipeline с нуля + глоссарий + запись + admin portal — объём значительно больше типичных проектов. Риск смещения сроков на 2–3 месяца.

**Митигация:**
- MVP scope строго ограничен: только WebRTC + перевод + базовый UI (Phase 1)
- Запись, глоссарий, admin portal — Phase 2, отдельный договор или допсоглашение
- Клиент видит working demo через 6–8 недель, не ждёт полного продукта 7 месяцев

**Ранний сигнал:** К 4-й неделе нет working WebRTC demo с базовым переводом.

---

## 6.3 Остальные риски

### T3 — Качество перевода фарм-терминологии 🟡
SeamlessM4T — модель общего назначения. Специфические термины могут переводиться неверно. Глоссарий покрывает только заранее известные слова.
→ **Митигация:** QA с реальным фарм-контентом с первого месяца; агрессивное наполнение глоссария до go-live (цель: >2000 терминов).

### P3 — Scope creep 🟡
Клиент добавляет пожелания ("а можно субтитры?", "а интеграцию с нашей системой?") без согласования стоимости.
→ **Митигация:** Процедура change request прописана в договоре до старта. Любое изменение scope = отдельная оценка и допсоглашение.

### T5 — Mac Studio / PyTorch MPS нестабилен 🟡
MPS backend значительно менее зрелый чем CUDA. Возможны memory leaks и несовместимости.
→ **Митигация:** RTX-сервер остаётся primary рекомендацией. Mac Studio — alternative с явным disclaimer в документации.

### L2 — Клиент не предоставляет железо вовремя 🟡
Разработка ведётся на "симуляторе" → production latency совсем другая.
→ **Митигация:** В договоре: клиент обязуется предоставить доступ к production-железу до старта разработки, или аренда сервера за счёт клиента.

### E1 — Дефицит GPU на сером рынке 🟡
RTX 5090 или DGX Spark внезапно недоступны или дорожают вдвое.
→ **Митигация:** Прописать в договоре 2–3 альтернативные конфигурации железа. Цены в смете — ориентировочные.

### E2 — LiveKit меняет лицензию 🟢
LiveKit уже менял условия self-hosted в 2024. Риск повторения.
→ **Митигация:** Абстрактный SFU-слой в архитектуре — замена на mediasoup/Janus без переписывания pipeline.

# 7. Результаты нагрузочного тестирования

> Тестирование проведено: 23 февраля 2026
> Стенд: NVIDIA GeForce RTX 4090 (24 GB), WSL2, Python 3.12, SeamlessM4T v2 Large (FP16)
> Методология: N WebSocket-клиентов в одной комнате, все отправляют 2-секундное аудио одновременно, замер e2e latency от отправки до получения переведённого аудио.

---

## 7.1 Эволюция архитектуры pipeline

В ходе тестирования последовательно проверены три подхода к обработке translation pipeline.

### Подход 1: Sequential (последовательная обработка)

Переводы для всех участников выполняются один за другим в одном потоке.

| Участников | E2E min | E2E avg | E2E max | RTF |
|:---:|:---:|:---:|:---:|:---:|
| 2 | 415ms | 641ms | 867ms | 0.20–0.22 |
| 4 | 535ms | — | 5014ms | 0.17–0.25 |

**Вывод:** Быстро при 1–2 участниках, деградирует при одновременных запросах.

---

### Подход 2: Thread Pool (параллельные потоки)

Переводы запускаются параллельно через `ThreadPoolExecutor`, но GPU один — потоки конкурируют за вычислительный ресурс.

| Участников | E2E avg | E2E max | RTF |
|:---:|:---:|:---:|:---:|
| 2 | 1492ms | 1538ms | 0.71–0.75 |
| 4 | 3941ms | 5091ms | 1.1–1.9 |
| 6 | 5524ms | 8092ms | 1.0–1.7 |
| 8 | 6934ms | 11044ms | 0.8–1.9 |

**Вывод:** Хуже sequential — конкуренция потоков за GPU увеличивает время каждого вызова.

---

### Подход 3: Batch Inference + Queue ✅ Финальная архитектура

Центральный воркер собирает входящие запросы в окне 150ms, группирует по парам (src\_lang → tgt\_lang) и отправляет каждую группу как **один батч** в `model.generate()`. Разные языковые пары обрабатываются параллельно через `asyncio.gather`.

| Участников | E2E min | E2E avg | E2E max | Generate (batch) | RTF |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 2 | 1079ms | 1336ms | 1593ms | 485–889ms | 0.26–0.45 |
| 4 | 687ms | 1764ms | **2749ms** | 371–460ms | 0.19–0.24 |
| 6 | 836ms | 1863ms | **2814ms** | 342–548ms | 0.18–0.29 |
| 8 | 813ms | 1997ms | **3064ms** | 349–537ms | 0.18–0.28 |

**Ключевой результат:** 3–4 аудио в одном батч-вызове `generate()` занимают ~400–550ms — почти столько же, сколько один аудио последовательно. GPU используется максимально эффективно.

---

## 7.2 Реальные сценарии использования

В боевых условиях конференции участники **не говорят все одновременно**. Типичный паттерн: 1–2 активных говорящих в любой момент.

| Сценарий | Активных говорящих | E2E latency | Оценка |
|----------|:-----------------:|:-----------:|:------:|
| Норма (1 говорящий) | 1 | ~500–900ms | ✅ Отлично |
| Активная дискуссия (2 говорящих) | 2 | ~800–1600ms | ✅ В рамках SLA |
| Стресс (все говорят, 6 участников) | 6 | max 2814ms | ⚠️ Незначительно выше SLA |
| Экстремальный стресс (все 8) | 8 | max 3064ms | ⚠️ Только при полном overlapping |

**Вывод:** Целевой SLA ≤2s выполняется при реалистичных условиях использования. Максимум 3s достигается только в искусственном стресс-тесте (все 8 участников говорят одновременно).

## 7.3 Производительность GPU

| Метрика | Значение |
|---------|---------|
| **GPU** | NVIDIA GeForce RTX 4090 (24 GB GDDR6X) |
| **Модель** | SeamlessM4T v2 Large (FP16, ~12 GB VRAM) |
| **RTF (batch, реальный)** | **0.18–0.29** |
| **Generate latency (1 аудио)** | ~400–550ms |
