# Rate limit, concurrency и другие слова которые сломали нам субботу

*Технические грабли, о которых никто не предупреждает, когда строишь продукт на AI-API*

---

Суббота. MVP задеплоен. Пайплайн генерации карточек работает. Настроение — победное. Запускаем первую серию генераций.

Одна карточка — ок. Вторая — ок. Третья — таймаут. Четвёртая — таймаут. Пятая — ошибка. Настроение падает быстрее, чем запросы.

## Что случилось

Мы мигрировали с Replicate на fal.ai. Причина прозаическая — на Replicate закончились кредиты. fal.ai предлагает ту же модель (Nano Banana Pro) по сопоставимой цене.

Миграция прошла быстро — API похожие, адаптировали обёртку за пару часов. На одном запросе за раз всё работает. Проблема появилась при параллельной генерации. Два запроса — ок. Три — один падает.

Первая мысль: RPM (requests per minute). Стандартное ограничение, встречается везде. Добавили `sleep(2000)` между запросами. Не помогло. Увеличили до пяти секунд. Не помогло. Экспоненциальный backoff — не помогло. Проверили статус fal.ai — всё зелёное.

Потратили несколько часов на чтение документации, экспериментирование и переписку с поддержкой. Ответ нашёлся не в quick start, не в examples — в глубине раздела про лимиты:

> Free tier: 2 concurrent requests.

Не 2 запроса в минуту. Не 2 в секунду. **2 одновременно.** Третий запрос встаёт в очередь на стороне fal.ai и может отвалиться по таймауту. Разница между RPM и concurrency — принципиальная. RPM решается задержками между запросами. Concurrency — семафором с контролем параллелизма.

Решение:

```javascript
const semaphore = new Semaphore(2);
async function generateCard(params) {
  await semaphore.acquire();
  try { return await falApi.generate(params); }
  finally { semaphore.release(); }
}
```

Десять строк кода. Суббота на разбор. Соотношение усилий к результату — впечатляющее. Но зато теперь мы точно знаем, что ищем, когда интегрируем новый API.

## Другие грабли, о которых не пишут

**Docker overlay network умирает от рестарта.** Рутинный `docker restart` может уронить виртуальную сеть. Контейнеры работают, но перестают видеть друг друга. PostgreSQL возвращает `EHOSTUNREACH`. Диагностика — час, починка — запись в БД Docker в три часа ночи. На Хабре мы написали об этом подробнее.

**Image-to-image модели додумывают детали.** Загружаешь фото чёрной куртки без логотипов. Получаешь куртку с нашивками, вышивкой и логотипом несуществующего бренда. Модель «знает», что куртки обычно с нашивками, и услужливо их добавляет. Михаил написал: «Это другая куртка.»

**AI-агент может добавить код не в тот проект.** Наш агент Дмитрий однажды добавил блок не на тот сайт. Heartbeat сработал дважды, агент «проснулся» два раза — и один из экземпляров решил, что целевой репозиторий другой.

**Embedding-модели не бесплатны.** Семантический поиск по памяти агента использует embedding'и. Каждый поисковый запрос — вызов API. При активной работе агента, когда он ищет в памяти контекст по нескольку раз за heartbeat, эти «копейки» складываются в заметную сумму.

**Таймауты по умолчанию — ловушка.** Дефолтные таймауты в SDK часто слишком длинные для продакшена. Генерация изображения может занять 30 секунд, а таймаут стоит 120. Пользователь уже ушёл, а ваш сервер всё ещё ждёт ответа.

## Совет тем, кто строит на AI-API

**Читайте раздел про лимиты ДО интеграции.** Не quick start, не examples — именно limits. Concurrency, rate limits, payload size, timeout. Всё это влияет на архитектуру, и узнавать об этом в субботу вечером — не лучшая стратегия.

**Тестируйте параллельную нагрузку сразу.** Один запрос — не тест. Десять параллельных — тест. Именно так всплывают concurrency-лимиты, таймауты и проблемы с очередями.

**Имейте plan B для каждого API.** Replicate закончился — перешли на fal.ai. Если fal.ai упадёт — должна быть альтернатива. Vendor lock — враг стартапа на ранней стадии.

**Логируйте всё.** Мы поняли проблему только когда посмотрели на таймлайн запросов — два успешных, третий висит, пока первые не завершатся. Без логов гадали бы ещё день.
